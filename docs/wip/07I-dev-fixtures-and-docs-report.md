## 2. `magnetico dev seed-torrents`

**Dataset** `magnetico-dev-fixtures-v1`: 101 torrents, 13,279 files — 40 single-file, 60 multi-file (10–100 files, both bounds occur), one torrent with exactly 10,000 files. Generated by a fixed-seed SplitMix64 (its sequence is fixed by the algorithm, unlike `math/rand`), infohashes are SHA-1 of `version/key`. Coverage: sizes from 1 byte to 3 TiB; discovery times over 2019–2026 with shared timestamps (ordering ties); ASCII, Cyrillic, Japanese, emoji and special-character names; one very long name; ten multi-file layouts (flat, seasons, deep chains, wide fan-out, Unicode, special characters, ~240-byte components with paths over 1 KiB, duplicate `(path, size)` pairs and same-path-different-size, file/directory clashes with literal `.`/`..` components and, once, leading/trailing/doubled slashes that force the codec's flat/prefix fallback, zero-size files); the no-blob single-file shape and atypical single files; the large torrent has 80×100 files, a flat 1,500-file directory and a six-level hierarchy. 100 torrents (≤ 4,000 files) use the web UI's full-tree mode, the large one the paginated-directory mode.

**Production APIs only.** Every fixture goes through `persistence.Store.AddTorrent` (real validation, real wire-format-v1 codec and transactions); no storage format of its own, no network code.

**Safety contract**

| Property | Behaviour |
|---|---|
| Target | `--database` or `MAGNETICO_DEV_DATABASE`; **required, no default**, never inherited from `migrate`/`web` settings (flag, environment or config file) |
| Confirmation | `--confirm-development-database` required for a write (CLI only); `--dry-run` runs every check and writes nothing |
| Schema | verified read-only first (`persistence.MakeDatabase`); missing, legacy, partial or wrong-version schemas are refused and never created, altered or migrated; no other schema touched |
| Populated databases | allowed only if the database holds **no** torrents or **only** fixture torrents (existing count must equal the number of fixture hashes present); any other torrent → `ErrForeignTorrents`, nothing written. A fixture hash stored with different metadata → `ErrFixtureConflict` |
| Repeat runs | complete dataset: reported no-op (`database was seeded … added 0`); interrupted (fixture-only, some missing): adds exactly the missing ones; existing rows never rewritten; nothing is ever updated, deleted or truncated |
| Concurrency | session advisory lock (key `7881644658832750190`) → `ErrBusy`; the count check and the inserts are not one transaction, documented (do not run ingest against the same database) |
| Startup | never run automatically; no hook in startup or schema initialization |
| Output | redacted URL (scheme, host, path), counts and state only; refusals use fixed messages |

## 4. Documentation: how it was checked

- **CLI flags and variables.** Every command and flag in the three guides was checked against `--help` of the built binary (dev, torrents, retry-errors, errors export, cleanup, users, users verify, verify-content, check-queue, ingest-schema-init, web user) and against `opflags/`.
- **Ingest and crawler.** `magnetico ingest` was started against a disposable database with a generated token: no token → `401`, `GET` → `405`, token + empty `info_hashes` → `200 {"exists":[],"missing":[],"unknown":[]}` (the guide's pre-flight `curl`). `crawl check-queue` on a missing directory exits 2 as documented. The crawler's unknown-environment-variable behaviour was observed (`MAGNETICO_CRAWL_FOO` rejected; the rule applies to `MAGNETICO_CRAWL_*` only, so `MAGNETICO_INGEST_*` on the crawler machine is ignored, which the guide states). Ports and flows come from the code (`dht/mainline`, `metadata/btconn`, `internal/crawler`, `internal/ingest/server`); `crawl` itself was **not** run (it would generate DHT/BitTorrent traffic) and the live-DHT acceptance remains deferred, as the guide says.
- **Migration guide ↔ implementation.** Commands, environment variables, exit codes (`torrents` 0/2/1; verifications 0/3/2/1; `retry-errors` 0/3/2/1), the W8 flow (`--dry-run`, `--source-writes-stopped`, `--accept-needs-reset`, `--replace-users --confirm-plan`, `--delete-unmatched-user-ids`, `verify`, `web user set-role`) and the refusal classes were taken from `main.go`, `opflags`, `docs/web-deployment.md` §10 and the 07H report. Not re-run end to end here (that is what the existing W8 and 04A–04D suites do).
- **A fix to the draft guide found by reading the gates.** `migrate cleanup` gate G5 reconciles the target's torrent/blob counts with the recorded import counters and is never waivable, so cleanup is impossible once ingest has stored a new torrent next to the migrated ones. The guide therefore decides cleanup **before ingest starts** (§8.3) and states what remains afterwards (§10). This is derived from `internal/migration/state.Reconcile` and `forensics/cleanup.go`, not exercised by a new test.
- **Links.** A script checked every relative link in `README.md`, `UPGRADE.md`, the three new guides and `docs/wip/README.md`; section references inside the migration guide were checked against its headings.
