# Task 09 — Ingestion Statistics and Read-Only Administration UI: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** plan, **revision 2** (2026-11-25), after the owner's review of revision 1 (twelve review items), the owner-directed per-crawler authentication amendment, and the authentication/batching clarifications. **No implementation has started.** Nothing in this plan authorises a tag, a push, a publication, a production database or a live-DHT run.

**Goal:** Individually provisioned crawler credentials stored in PostgreSQL (replacing the shared ingest token); bounded in-memory ingest instrumentation; a periodic idempotent writer into a new versioned PostgreSQL statistics schema (hourly/daily/monthly aggregates, per-instance snapshots, shared queue/storage state, per-crawler activity); batched, connection-reusing crawler delivery; a cached read model; and a read-only administrator section (dashboard with five uPlot chart groups, crawlers, quarantine, users, invitations, trackers).

**Architecture:** `crawler —Bearer mgc_… → ingest`: the credential authenticates and **is** the identity (digest lookup, 60 s positive cache). Every ingest event is recorded under one short mutex-protected critical section into an hour-keyed accumulator (no I/O on the request or consumer path). One writer per ingest process drains it into a writer-local carry, seals immutable numbered batches, and applies them with additive upserts guarded by a conditional per-instance sequence update. Shared gauges (queue, quota, storage) are sampled only by the instance that owns the queue consumer and are stored as single shared state, never summed. `magnetico web` reads that schema through a coalescing, last-known-good cache and renders admin pages server-side; charts are vendored uPlot driven by first-party vanilla JS. Single binary, separate deployments, no new infrastructure.

**Tech stack:** Go ≥ 1.27.4 (standard library, `pgx/v5` already in use; no UUID dependency: UUIDv4 from `crypto/rand`), PostgreSQL 17, html/template, vendored uPlot (MIT).

**Specs read (binding authority, in this order):** this task's brief and the owner's amendments (below); `AGENTS.md`; `docs/engineering-standards.md`; `docs/specs/crawler-ingest-delivery-v1.md` (§4–§10); `docs/specs/web-v1.md` (§2, §4, §5, §6); `docs/specs/postgresql-persistence-v2.md`; `docs/wip/07J-*` (accepted); `docs/wip/08-ci-oci-report.md`; `docs/wip/rc0-acceptance-checklist.md`. Forgejo: #48 (Admin UI proposal), #50 (statistics collector), #49 (invitation graph, deferred). Design ideas reused from `skobkin/meshmap-lite` (`internal/stats` job shape: catch-up on start, retry delay, UTC calendar buckets; typed TTL cache invalidated by the writer).

## Global Constraints

Copied from the brief and the owner's amendments (every task includes them):

- Use the existing PostgreSQL deployment; no Redis, TimescaleDB, Prometheus, external metrics service or other required infrastructure. **No new externally exposed metrics endpoint.**
- **No new database connection from the crawler.** No database writes per request or per processed torrent solely for statistics. No persistent event log. **No persistent association of a crawler with a torrent or info hash.** No torrent names, file paths, metadata payloads, credentials, token hashes or request bodies in statistics.
- Bounded memory, predictable database growth, bounded query cost — **independent of the number of registered crawlers**. Statistics failures must not interrupt ingestion, change admission decisions, compromise durability or prevent crawler delivery, **and never affect authentication**. No new dependency in the crawler's critical DHT path.
- Authentication: exactly **one** valid token per crawler (permanent design decision; rotation replaces the credential); server-generated stable UUIDv4 and unique human-readable name; token = `mgc_` + ≥ 32 bytes of `crypto/rand`; only the SHA-256 hash is stored; identity derives **only** from the authenticated credential; Bearer transport and metadata JSON unchanged; `MAGNETICO_CRAWL_INGEST_TOKEN` stays; `MAGNETICO_INGEST_TOKEN` is removed with **no** compatibility fallback; ingest protocol stays v1; no automatic registration, no second token, no token expiry, no web mutations in 0.8.0; credentials are revealed once and never appear in listings, logs, statistics or the Admin UI.
- Positive authentication cache: keyed by token digest, bounded, **fixed non-sliding TTL of 60 seconds**, never extended by use or by database failure, no plaintext, coalesced lookups, bounded lookup concurrency and deadlines including invalid credentials; a propagation delay of up to 60 s for revoke/disable/rotate is accepted and documented.
- Versioned statistics schema (isolated); explicit initialisation and verification; **no automatic destructive migration**; the default shared PostgreSQL account deployment stays supported.
- UTC for storage and bucket boundaries; hourly, daily and monthly aggregates kept **indefinitely**; counts and sums for counters, sum+count for weighted averages, min/max/last for gauges, coverage information; never average averages or percentages without weights.
- Intervals: queue sampling 10 s, snapshot 10 s, aggregate persistence 60 s, storage sampling 5 min, web snapshot cache ≈ 10 s, chart cache ≈ 60 s; few knobs.
- Admin UI is server-rendered, custom CSS, vanilla JS; `Admin` link next to the account link, administrators only; role enforced server-side on every route, JSON endpoint and data-access function; read-only (no mutation, unsupported methods refused); no password or credential hashes, session secrets, raw tokens or **crawler token hashes**; unused invitation codes never shown; quarantine payloads never shown.
- uPlot vendored (JS, CSS, licence, version, checksum) like Swagger UI, **licence shipped in the OCI image and the GoReleaser archives and checked**; no CDN, no framework, no Node build; the existing CSP is kept, never weakened; light and dark themes; no-data and error states; textual summaries. Live updating is deferred to 0.9.0.
- Transport and batching: keep the HTTP request-response protocol and durable-delivery guarantees; do not compromise SQLite durability, acknowledgement semantics, shutdown behaviour or queue recovery; the record-count and payload-byte limits are protocol constraints.
- Go ≥ 1.27.4; all of Task 08's gates stay green (`golangci-lint` 0 issues, `go vet` with tags, the skip census, `internal/repocheck`); no release build passes `-tags`; production code exports nothing only for tests.
- No live DHT, no production database, no tags, pushes or publication. Commit as the configured git identity with the `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>` trailer.

## Design decisions and trade-offs

Each decision lists what it costs. Rulings made during execution are ledgered as `Ruling:`; these are made now so the owner can overturn them before code exists.

**D1. Schemas.**

*D1a — `magnetico_ingest` version 2 (mandatory, holds authentication).* New table `crawlers`: `crawler_id uuid PRIMARY KEY` (server-generated UUIDv4), `name text NOT NULL` (1–64 chars, `^[A-Za-z0-9][A-Za-z0-9._-]*$`, **unique case-insensitively** through a unique index on `lower(name)`), `token_hash bytea NOT NULL UNIQUE CHECK (octet_length = 32)`, `enabled boolean NOT NULL`, `created_at`, `token_rotated_at`, `disabled_at timestamptz`. No triggers. Statistics are **not** here. `ingest_version` becomes exactly **{2}**.
*Upgrade of an existing (development) database:* `migrate ingest-schema-init` on a v1 schema performs an **additive, transactional upgrade** under the advisory lock — `CREATE TABLE crawlers`, version row `1 → 2` — touching neither `queue` nor `quarantine` nor `usage`, so queued data survive (tested with rows present and with `usage.used_bytes` unchanged); on v2 it is a no-op; on anything else it refuses. `ingest` and `web` verify v2 and print `run migrate ingest-schema-init` for v1 (never auto-upgrade, never repair). Explicit reinitialisation of a development database stays a manual, documented operator action (`DROP SCHEMA magnetico_ingest CASCADE` after the queue is drained); nothing destroys data silently. After an upgrade **no crawler exists**: ingest starts, logs one warning ("no enabled crawler is registered"), and every request is 401 until `ingest crawler add` is run — no restart needed, because an unknown digest always goes to the database. *Cost:* a schema bump on an unreleased schema; an operator step on every development database.
*D1b — `magnetico_stats` version 1 (optional, statistics only).* Created by `magnetico migrate stats-schema-init`, same pattern as `ingest-schema-init` (idempotent, advisory lock, requires a verified `magneticod` v1, structural verification, fail closed, no repair). `ingest` and `web` **start without it** (one warning; the dashboard says "statistics schema not initialised"); its absence, a wrong version, revoked grants or the kill switch never touch authentication or admission. Tables in D5–D7.
*Grants:* ingest runtime role: `SELECT` on `magnetico_ingest.crawlers` (authentication lookup) plus its existing queue DML; the operator role running `ingest crawler …` needs DML on `crawlers` (default shared account: everything); web role: **column-level** `SELECT (crawler_id, name, enabled, created_at, token_rotated_at, disabled_at)` on `crawlers` (never `token_hash`) and the quarantine columns below. *Cost:* three schemas, three grant sets, two init commands.

**D2. Authentication.**
- Order in `preflight` is kept: method → **authentication** → content type; the body is never read before authentication succeeds.
- `crawlerauth.Authenticator.Authenticate(ctx, bearer string) (Identity{CrawlerID, Name}, error)` with typed errors `ErrUnauthorized` (missing, malformed, unknown or disabled — one response, no oracle: `401 unauthorized`, `WWW-Authenticate: Bearer`) and `ErrUnavailable` (database error, timeout or saturation → `503 storage_unavailable`, or `503 busy` when the lookup slots are saturated, both retryable with `Retry-After`; **never** a false 401). The bearer string is hashed immediately; plaintext is never stored, cached or logged.
- Lookup: `SELECT crawler_id, name, enabled FROM magnetico_ingest.crawlers WHERE token_hash = $1` (unique index; no scan). A disabled row yields `ErrUnauthorized` (and the crawler id is kept for the *rejected request* counter of that crawler; it is never cached).
- **Cache:** positive only, key = 32-byte digest, value = identity + `fetchedAt`; fixed TTL **60 s from `fetchedAt`** (never refreshed by use); ≤ 4,096 entries (oldest-fetched evicted; far above any realistic crawler count and a hard memory bound); expired entries are revalidated against PostgreSQL and a database failure does **not** extend them (the request fails 503). Concurrent lookups of one digest are coalesced (`singleflight`). Within the TTL a revoked, disabled or rotated credential still authenticates (**accepted ≤ 60 s propagation delay**); a *new* credential works at once (its digest is not cached, so the lookup finds it).
- **Bounded concurrency:** at most **8** concurrent lookups (non-blocking slot with a ≤ 250 ms wait, then `503 busy`), each with a **2 s** deadline. A flood of invalid tokens therefore cannot hold more than 8 connections; cached identities of healthy crawlers keep working. *Cost:* during such a flood an uncached healthy crawler may get 503 and retries (crawler backoff exists).
- No negative cache (not requested; it would make a rotation less predictable). *Cost:* every repeated invalid token costs one indexed lookup, bounded by the slots.
- The recorder receives the `CrawlerID` from the authenticated request context; there is no other source of identity.
- **CLI** (operator-only; connects with `--database`, or `--queue-database` when set; DSNs and hashes never printed): `magnetico ingest crawler add <name>` (prints the UUID, the name and the token **once** on stdout; the token is not recoverable), `list` (UUID, name, enabled, created, token rotated, disabled — **no** token, no hash), `disable <name>`, `enable <name>`, `rotate-token <name>` (replaces the hash in one `UPDATE … RETURNING`; same UUID; works on a disabled crawler without enabling it; prints the new token once). Each command states the ≤ 60 s propagation delay for running ingest instances. Names are resolved case-insensitively; unknown name → controlled error. `opflags` gives `ingest` `subcommands-optional:"true"` like `web`.
- Removed: `MAGNETICO_INGEST_TOKEN` (its presence is a clear startup error naming the replacement, not a silent ignore), `server.Config.Token`, the shared digest.

**D3. Events and boundaries.** (`bytes` = HTTP **request-body** bytes actually read; not TLS, headers or responses.)

| Metric | Recorded at | Definition |
|---|---|---|
| `submit_requests_authenticated` | after authentication succeeded | HTTP requests (any outcome) |
| `submit_requests_validated` | after the envelope decoded **and** every record validated | the denominator of "records per request" |
| `records_received` | same moment | records in validated requests, **before** admission (includes records later refused or duplicate) |
| `records_enqueued`, `admission_duplicates` | `Admit` returned nil (the 202 path), from `AdmitResult` | rows inserted / already pending |
| `records_acknowledged` | same | `enqueued + admission_duplicates` exactly |
| `records_refused_at_admission` | `Admit` returned an error (`queue_full`, storage error, cancelled) | `received = acknowledged + refused_at_admission` exactly |
| `requests_rejected[class]` | `writeError` call sites | HTTP **requests**; nine fixed classes (below). Their records are counted only where a decoded count exists (`refused_at_admission`); requests refused before decoding contribute no record count |
| `bytes_body` | counting reader around `MaxBytesReader` | both endpoints, authenticated requests only |
| `bytes_accepted_payload` | `Admit` (`RETURNING payload_bytes`) | payload bytes of **inserted** rows; mean record size = this ÷ `records_enqueued` |
| `exists_requests`, `exists_hashes`, `exists_found/missing/unknown` | `handleExists` | requests; hashes checked; per-hash outcomes. Mean hashes per request = `exists_hashes ÷ exists_requests` |
| `cache_hit_positive/negative`, `cache_miss` | `existence.Service.Check` per hash | hit rate = (pos+neg) ÷ (pos+neg+miss) |
| `auth_cache_hits`, `auth_cache_misses`, `auth_db_lookups`, `auth_storage_failures` | `Authenticator` | hits; misses (absent or expired, including coalesced waiters); actual queries; failed lookups (timeout, error, saturation) |
| `processing_attempts`, `processing_retries`, `processing_storage_errors` | consumer | attempts started / rescheduled / globally backed off |
| `torrents_created` | `AddTorrent` returned `created = true` | **creation boundary**: counted the moment the torrent exists, whatever happens to the queue row afterwards |
| `settled_stored_new`, `settled_stored_existing`, `settled_quarantined` | **after** the queue-row `DELETE` / quarantine move committed | **settlement boundary**, mutually exclusive: the row left the queue. `new`/`existing` is what the **settling attempt's** `AddTorrent` reported |
| `processing_ms_sum/count` | settled-stored | claim-to-delete wall time; mean = sum ÷ count |

Why two boundaries: if `AddTorrent` creates a torrent and the following `DELETE` fails, the retry reports `existing`. `torrents_created` already counted it (exact creation count by this deployment, apart from a process crash between the commit and the increment: undercount, documented); the settlement chart records one `stored_existing` for that row (documented: "existing" includes torrents created by an earlier attempt). The **outcomes chart stacks the three settlement outcomes only**, which are mutually exclusive by construction; `torrents_created` is a separate line/figure. Operational telemetry only: the durable protocol and per-torrent attribution are untouched.

Reject classes (fixed ordinals; a new class is a schema bump): `auth` (401), `unavailable_auth` (503 `storage_unavailable`/`busy` raised by the authenticator), `malformed` (405, 415, `invalid_request`, `invalid_batch`), `too_large` (`payload_too_large`, `record_too_large`), `invalid_record` (`invalid_record`, `unsupported_version`), `queue_full`, `storage_unavailable`, `busy`, `internal`. Requests rejected before authentication succeeds have no crawler and count globally only; a disabled crawler's rejected request is also counted for that crawler.

**D4. Recorder concurrency and event-time attribution** (items 1–2).
- `Recorder` owns one `sync.Mutex`. **Every** recording method takes it, updates plain (non-atomic) fields — the hour counters, the 1 s/1 min rings, the per-crawler map — and releases it. **No I/O, no blocking call and no allocation beyond a bounded map insert occurs inside.** A method that touches several related counters (`SubmitAcked`, `SubmitRefused`, `SettledStored…`) updates them in **one** critical section, so a rotation sees the whole event or none of it and `received = acknowledged + refused` holds in every drained `Delta`.
- `Drain()` takes the same mutex, moves the accumulator out (`cur, rec.cur = rec.cur, newAccum()`) and releases it. A recorder that arrives later writes to the **new** accumulator; one that held the lock finished before the swap. A detached accumulator is never written again, so nothing can be lost or double-counted (this replaces the revision-1 "atomic pointer swap", which did not have that property). Contention is bounded by the sub-microsecond section and **measured** (acceptance criteria), not assumed.
- **Attribution by event time:** the hour of an event is computed **inside** the critical section from the injected clock: `hour = max(hourOf(now), lastHour)`. The accumulator is keyed by UTC hour (`map[hour]*HourCounters`, ≤ 26 live keys), so a late timer tick, a blocked writer, a slow flush or a ticker that fires after the boundary cannot move an event into another bucket: the event is already in its own hour. Day and month are derived from the hour (a UTC hour never spans a day or month). **Clock adjustments:** a backward step cannot produce an hour older than one already used (the clamp keeps the event in the latest hour — documented); a forward step leaves empty hours, which have **no row** (a missing observation); a step of more than 26 hours either way marks the writer `clock_anomaly` and keeps attributing to the latest hour. Gauge samples carry their own sample time and follow the same rule.
- Coverage (`observed`) is **not** derived from flush times: it is the set of UTC **minutes** during which the process was running and recording (D7).

**D5. Flush protocol: sealed immutable batches** (item 3). *Tables:* `ingest_instances(instance_id uuid PK, started_at, last_flush_seq bigint NOT NULL, last_flush_at, heartbeat_at)`.
1. Writer-local state (one goroutine): `carry` (a `Delta` that newer drains merge into) and at most one `sealed` batch `{seq, delta, attempts, inDoubt}`. **A sealed batch is immutable from the moment it is first attempted; nothing is ever merged into it** (not even a newer hour). Newer observations go to `carry` and are sealed as `seq+1` only after `sealed` is resolved.
2. One transaction per attempt (`lock_timeout 5 s`, `statement_timeout 10 s`, `idle_in_transaction_session_timeout 15 s`):
   a. `UPDATE ingest_instances SET last_flush_seq = $seq, last_flush_at = now() WHERE instance_id = $id AND last_flush_seq = $seq - 1` — **its affected-row count is checked before any other statement**. This statement takes the instance row lock, held to commit: a second transaction for the same batch (a retry racing an in-flight commit) blocks on it and, after the first commits, matches **zero** rows.
   b. 1 row ⇒ apply the hour, day and month upserts (D6, D7) and the per-crawler upserts, `COMMIT`.
   c. 0 rows ⇒ **no delta is applied**; read `last_flush_seq`: `== $seq` ⇒ the batch already committed (resolved: drop it, count `resolved_committed`); row missing ⇒ see below; anything else ⇒ see below.
3. **Error classes:** an error before `COMMIT` was sent (acquire, statement, rollback) ⇒ not committed, retry the **same** batch. An error while sending `COMMIT` or a lost connection after it ⇒ `inDoubt = true`; the retry is the same sealed batch, and step 2a/2c decides — no separate "read the sequence" heuristic is needed, because the conditional `UPDATE` is the single arbiter, and a still-running old backend that later commits makes the retry's `UPDATE` wait on its row lock and then match zero rows.
4. **Anomalies (all deterministic, none apply a delta):**

| Observed | Meaning | Action |
|---|---|---|
| row missing, batch **never in doubt** | the row was removed (manual action, prune after a >30-day outage) | recreate it with `last_flush_seq = seq − 1` (`INSERT … ON CONFLICT DO NOTHING`) and retry once |
| row missing, batch **in doubt** | cannot tell whether it committed | **drop** the batch (undercount, never double-count); count `batches_dropped_unresolved`; recreate the row at `seq` |
| `last_flush_seq` ≠ `seq` and ≠ `seq − 1` | foreign write or corruption | drop the batch, count `sequence_anomalies`, log once loudly, resynchronise `lastSeq` from the database, continue with new batches |
| batch older than 24 h (outage) | bounded buffer | drop, count `hours_dropped`; at most 26 hour-buckets are ever buffered |

5. **Housekeeping cannot delete a live writer's state:** pruning of `ingest_instances` is done by writers after a successful flush: `DELETE … WHERE instance_id IN (SELECT instance_id FROM ingest_instances WHERE greatest(last_flush_at, heartbeat_at) < now() − interval '30 days' AND instance_id <> $self FOR UPDATE SKIP LOCKED)`. Rows locked by an in-flight flush are skipped, and a batch is abandoned after 24 h, so no unresolved batch can outlive its row's 30-day grace. Snapshot rows older than 24 h are pruned the same way.
6. *Cost:* ≤ 60 s of measurements are lost on `SIGKILL` (only while periodic persistence succeeds; during an outage the buffered ≤ 24 h are also lost on a crash, item 9); a dropped unresolved batch under-counts, which is the safe direction.

**D6. Tables of `magnetico_stats` v1** (fixed-width numeric columns, no JSON, no labels, no crawler↔torrent association):

| Table | Key | Purpose / bound |
|---|---|---|
| `stats_version` | one row `{1}` | version |
| `ingest_instances` | `instance_id` | D5 |
| `snapshot` | `instance_id` | per-instance **heartbeat** state updated in place every 10 s: cumulative counters since start, completed-slot window counts with `covered_seconds` and `window_end`, cache and consumer stats, flush status counters (`hours_dropped`, `sequence_anomalies`, …); pruned after 24 h |
| `shared_state` | single row `id = 1` | **shared** database state: queue depth/bytes/quota/quarantine/oldest age with `queue_sampled_at` and flags; storage measures with `storage_sampled_at`; `gauge_last_slot`, `storage_last_slot` (D7). Overwritten only by a newer sample |
| `crawler_activity` | `crawler_id uuid` | per registered crawler, **no foreign key** to `magnetico_ingest` (different schema owner, survives disable/rotation): `first_seen_at`, `last_seen_at`, `last_ip inet`, `last_submit_at`, cumulative received/enqueued/duplicate records, body bytes, exists requests/hashes, rejected requests. One row per crawler that ever connected; bounded by the registered count (operator-controlled), never by traffic |
| `agg_hour`, `agg_day`, `agg_month` | `bucket_start timestamptz` (UTC, `CHECK` aligned) | counters (sum), weighted pairs (sum,count), gauges (sum,count,min,max,last,last_at), `covered_minutes` |
| `storage_hour`, `storage_day`, `storage_month` | `bucket_start` | the storage measures of D10 (`last`, `max`, sample sum/count) |

*Crawler-activity merge semantics (timestamp-aware):* `first_seen_at = LEAST(row, excl)`, `last_seen_at = GREATEST(row, excl)`, `last_ip` and `last_submit_at` replaced **only if** `excl.last_seen_at > row.last_seen_at` (a delayed batch never overwrites a newer value; an exact tie keeps the stored value); counters additive. Growth: one `agg_hour` row ≈ 0.7 KB → ≈ 6 MB/year plus index; the 1/5/10-year estimate is **measured** with generated rows and `pg_total_relation_size` (Task 11). Missing vs zero: no row = missing observation; a row with `covered_minutes > 0` and zero counters = measured zero. `CHECK` constraints keep counters ≥ 0 and `min ≤ max`; the reader rejects (and reports, not renders) rows that violate them.

**D7. Shared state, the elected sampler, coverage** (item 4).
- **Per-instance** data (event counters, windows, cache, consumer stats) is summed across instances; **shared** data (queue depth and bytes, quota usage, quarantine, oldest age, all storage sizes, the indexed-torrent estimate) describes the one database and is **never summed**: it lives in `shared_state`, one row.
- **Election:** only the instance whose queue consumer `Owns()` the advisory lock runs the queue and storage samplers (existing mechanism; failover is the consumer's own: when ownership moves the new owner's samplers start on their next tick, and the gap is a visible missing observation, not an error). A stale owner that has not yet noticed the loss is handled by the slot guard.
- **Slot guard (no overlapping contributions):** every shared sample has an integer slot (`unix_seconds / 10` for queue, `/ 300` for storage). The sample set of one flush is applied to `agg_*`/`storage_*` and `shared_state` **only if** its first slot is greater than `shared_state.gauge_last_slot` (`storage_last_slot`); the same statement advances the marker. A batch that overlaps an already-applied slot (a handover race) has its **shared-gauge part skipped** (counted `gauge_batches_skipped_overlap`; at most one minute of samples is lost), so two instances can never contribute the same period twice. Event counters in the same batch are applied regardless.
- **Coverage is a union:** each instance records the set of UTC **minutes** (bit i of a `bigint` per hour) in which it was running and recording; `agg_hour.covered_minutes` is merged with **bitwise OR** (idempotent, commutative; two instances in the same minute count once, so coverage can never exceed the bucket length). The day and month rows store a count: in the same transaction, `new_bits = excl & ~old_hour_bits` (the hour row is locked `FOR UPDATE` first; rows are always locked hour → day → month in ascending order, so concurrent writers cannot deadlock) and `day.covered_minutes += bit_count(new_bits)`. `observed_seconds` of revision 1 is dropped. *Resolution:* one minute; a minute counts as covered if the process recorded at any moment in it (overstates by < 1 min at an outage edge; documented). *Rejected:* summing per-instance seconds (can exceed 3,600).
- **Event-rate summation** across instances (D8) uses each instance's own count over its own covered time.

**D8. Rates, units and freshness** (item 9).

| Quantity | Formula | Unit shown |
|---|---|---|
| rolling rate, window `W` ∈ {60 s, 15 min, 60 min} | `Σ_i count_i(W) ÷ covered_i(W)` over **fresh** instances (snapshot younger than 30 s) with `covered_i ≥ W/2` and `window_end` within 30 s of the newest instance's; instances excluded by either rule are listed ("N instance(s) not included") | 60 s → per second; 15 min → per minute (× 60); 60 min → per hour (× 3,600) |
| completed calendar bucket | the stored **count** (never a rate) | per hour / day / month |
| average over a completed bucket | `count ÷ (covered_minutes × 60)` shown **only** when `covered_minutes > 0`, flagged "partial" below the full length | per second |
| current (open) hour | count so far, labelled partial | count |
| weighted means | `Σ sum ÷ Σ count` of the stored pairs | per metric (e.g. hashes per exists request) |

Rolling windows come from in-memory rings (60 × 1 s and 60 × 1 min, inside the D4 critical section); `covered_seconds` is how long this process has really observed that window. Persisted aggregates are the authority for completed periods; rolling rates are an operational display only.
**Three independent freshness clocks:** (a) *ingest instances* — `snapshot.published_at`: up < 30 s, stale < 5 min, else unavailable; (b) *queue state* — `shared_state.queue_sampled_at`: fresh ≤ 90 s, stale ≤ 15 min, else unavailable; (c) *storage* — `storage_sampled_at`: fresh ≤ 15 min, stale ≤ 1 h, else unavailable. A failed queue sample leaves (a) untouched: the instance stays "up" with queue fields shown "unavailable" and their age. Heartbeat publication is independent of the samplers (D9) and of the flush.
**Crash-loss statement (corrected):** "at most about 60 s of counters lost on a crash" holds **only while periodic persistence succeeds**; during a statistics-database outage up to 24 h of buffered hourly deltas are lost on a crash, and anything beyond the buffer bound is dropped (counted and shown).

**D9. Sampling correctness and isolation** (item 7). A separate **sampler pool** (one connection, same DSN as the queue; the flush/heartbeat has its own one-connection pool) so a slow sampler can never delay a flush or a snapshot; samplers run in their own goroutines and write into an in-memory *latest sample* that the heartbeat and the flush read non-blockingly.
- *Queue sample (every 10 s, elected instance only):* one `REPEATABLE READ, READ ONLY` transaction (a **consistent snapshot** of related gauges) with per-statement `statement_timeout 2 s` and a **cycle deadline of 5 s total**: `usage.used_bytes` (O(1), exact); `count(*), sum(payload_bytes), min(received_at)` of `queue`; the same for `quarantine`. `min(received_at)` is exact (the scan already happens for the count); it replaces the revision-1 `ORDER BY id LIMIT 1`, which is **not** the minimum of `received_at` under concurrent admissions.
- *Fallbacks are independent per quantity:* **counts** may fall back to the planner estimate (`reltuples`, flagged `approximate`); **byte totals** have **no** estimate (a row estimate cannot substitute for payload bytes) — on timeout the per-table bytes become *unavailable* while `used_bytes` (exact, combined) still drives quota utilisation; **oldest age** falls back to `received_at` of the lowest `id` (indexed; flagged `approximate`: it can differ from the true minimum by the length of an admission transaction) and otherwise is unavailable. Nothing is rendered as zero when unavailable.
- If a cycle exceeds 2 s the interval doubles up to 60 s (`queue_state_interval_backoff` flag). Whether exact counts are affordable at 100 k and 1 M queued rows is **measured in Task 6** (criteria below); no trigger or index is added to `magnetico_ingest` without an owner decision.
- *Storage sample (every 5 min, elected instance only):* catalog queries (D10) on the sampler pool with `lock_timeout 2 s`, `statement_timeout 5 s`, **cycle deadline 20 s**; no payload is read; needs catalog read and `CONNECT` only.
- A cycle that hits its deadline is abandoned; the previous sample stays and shows its age.

**D13. Failure behaviour.**

| Event | Behaviour |
|---|---|
| Statistics schema missing/invalid/unwritable/locked, or kill switch | one warning; writer disabled or backing off; **authentication and ingestion unaffected**; the dashboard says so |

**D16. Delivery batching and transport** (clarifications; optimised for background bulk delivery, not per-record latency).
- *Existence precheck:* `PrecheckLinger` 100 ms → **1 s**; `PrecheckBatch` 256 → **1,024** (the server maximum). The 4,096-entry hand-off channel holds four full batches; a test proves 1,024 hashes serialise below the 64 KiB `MaxExistsBodyBytes` and that the response of 1,024 hashes stays within its limits. A batch is dispatched when it holds 1,024 hashes or the linger (counted from the first element) expires; an empty batch is never sent.
- *Metadata submission:* **time-based** batching with early dispatch. The sender waits `SendLinger = 1 s` from the **oldest unsent record's `EnqueuedAt`** and sends whatever is queued up to the limits; it dispatches **early** when the selected payload bytes reach `SendMaxBytes` (8 MiB). The 256-record limit stays a hard protocol constraint (a batch never exceeds it) but is not a batching target. During **backlog recovery** (more than one full batch queued — by bytes or by count) full batches are dispatched back to back, one request in flight (the sender is sequential: concurrency and backpressure bounded as today). Steady-state target ≈ **one request per second per endpoint per crawler**. A `Wake` after an append no longer sends immediately.
- *Unchanged:* `Peek`/`Ack` after a 202 only, the bisect and quarantine rules, the 401/503/unrecognised pauses and backoff, SQLite durability and recovery. **Shutdown:** a pending linger is cut short, one last dispatch is attempted within the existing grace, and rows stay queued if it fails.
- *Connection reuse and HTTP/2:* a test using `httptrace` proves that consecutive requests reuse one connection (bodies drained and closed; the 2 idle connections and 90 s idle timeout versus the server's 120 s idle timeout checked). HTTP/2: over TLS the default custom `http.Transport` already negotiates `h2` (no custom dial or TLS config); the plan **verifies** that with a TLS test server, and **evaluates** cleartext HTTP/2 (`http.Protocols`, h2c) against the measured benefit at ≈ 1 request/s per endpoint (expected: none beyond keep-alive); the decision (keep HTTP/1.1 keep-alive for `http://`, rely on TLS `h2`) is recorded in the report with the measurement, and only a measured benefit changes the code.
- Metrics added in D3 make the effect visible: requests per second per endpoint, mean hashes per exists request, mean records per submit request.

- **Proportion:** decisions, signatures and test names only; no function bodies.

## Risks and open points for the owner

1. **Protocol/credential change** makes every pre-existing crawler fail until it is given a registered token (intentional; no deployed crawler exists). The shared token is gone with no fallback.
2. **`magnetico_ingest` becomes version 2** (additive upgrade of v1; queued data kept). A development database needs `migrate ingest-schema-init` once, and then `ingest crawler add`.
3. **Grants:** the ingest role needs `SELECT` on `crawlers`; the operator role needs DML on it; the web role needs column-level `SELECT` on `crawlers` (no hash) and on `quarantine` (no payload, no info hash); the default shared account needs nothing. Documented with verbatim `GRANT`s executed by the tests.
4. **The 60 s cache** accepts that a revoked or rotated credential keeps working for up to 60 s on every running ingest instance (documented in the spec and in each CLI command's output).
5. **Exact queue counts at scale** are unmeasured until Task 6; fallbacks are flagged, byte totals are never estimated, and no index or trigger is added to `magnetico_ingest` without a decision.
6. **uPlot under the strict CSP** and every visual property are unverifiable on this VM; they join the RC0 checklist. The packaged-archive and image licence checks are verified statically here; a real publication is not run.
7. **Event time is the ingest host's clock**: a host with a badly wrong clock produces misplaced buckets (documented; the monotone clamp and `clock_anomaly` expose it, coverage exposes gaps, not skew).
8. **A dropped unresolved batch under-counts** (safe direction) when its instance row is gone; counted and shown.
9. **Approximate indexed-torrent count** lags after bulk imports until autovacuum/analyze (labelled approximate).
10. **No cleanup for `crawler_activity` of crawlers that are never removed**: crawlers are only disabled in 0.8.0, so rows stay bounded by the registry.

## Execution handoff

Which approach: **native (inline) with one fresh whole-branch review** is the recommendation, as in Task 08: the twelve tasks share interfaces in one chain (credentials → authenticator → recorder → writer → schema → reader → admin), so a per-task fresh context would re-read the same code twelve times, while the mutation-checked tests and the final review carry the risk. Subagent-driven is the alternative if you want a review gate after each of Tasks 2, 6 and 8 (the three that touch the delivery and credential path, the persistence protocol, and the privilege boundary).
