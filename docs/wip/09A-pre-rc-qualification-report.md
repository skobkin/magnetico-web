## 3. Correctness findings and fixes

### 3.1 Advisory-lock collision

**Finding.** `migrate web-schema-init` took the same session-wide key (`7881644658832750187`) as the ingest consumer's session lock, so it blocked for as long as an `ingest` ran. **Inventory** of every advisory key in the repository (all other keys were already distinct): torrent schema init …185 (transaction), ingest schema init …186 (transaction), **consumer …187 (session)**, trackers write …188 (transaction; shared on purpose by the web-schema seed, the operator CLI and the development seed), users migration …189 (transaction), development seed …190 (session), stats schema init …191 (transaction), the migrator's run lock `4048864026886105453` (session). **Fix.** One registry, `internal/advisory`; `web-schema-init` moved to …192 (unreleased identifier, no migration). **Regression tests.** `TestInitDoesNotWaitForTheIngestConsumerLock` (RED: timed out waiting for the consumer's key), `internal/repocheck` `TestAdvisoryLockKeysAreDeclaredOnceAndDistinct` and `TestAdvisoryLocksUseOnlyTheRegistry` (RED: the duplicate value and nine key literals outside the registry), `internal/advisory` (positive, unique).

### 3.2 Admin read-model cache

**Findings.** (1) `get` kept a pointer to the entry it had looked at before waiting; a later successful load updated that same entry in place: a **data race** (reproduced with `-race`, the read of `old.v` against `storeLocked`) and a possible mismatch of a value with another load's fetch time. (2) Coalescing bounded loads per key only: a burst of distinct, attacker-influenced keys (chart, granularity, period) could start unbounded concurrent database loads. (3) A cached overview kept the ages and states it had at read time: after a failed refresh the last known good reported a stale heartbeat as "up", and an expired queue or storage sample still showed numbers. (4) The crawlers page and the charts did not say that the data was cached or old.

**Fixes.** Entries are immutable once published (a refresh replaces them) and the newest last-known-good is served with **its own** fetch time; at most 4 loads run at once and 32 exist at all (`ErrBusy`, or the stale value, beyond that), the load deadline covers the wait for a slot; coalescing, cancellation, deadlines, bounded memory and last-known-good are kept. `Overview.aged` re-classifies every state at the time of serving (instances, queue, storage, rates, the open hour) and blanks an expired sample; `CrawlerPage.aged` does the same for crawler activity. The crawlers page states when it was read and warns when it is the last known good; each chart carries the same caption. **Tests** (race detector): `TestCacheEntriesAreImmutableAfterPublication` (RED: data race), `TestCacheReturnsTheFetchTimeOfTheValueItServes`, `TestCacheBoundsConcurrentLoadsForDistinctKeys`, `TestCachePendingLoadsAreBoundedAndAnswerBusy`, `TestCacheLoadDeadlineCoversTheWaitForASlot`, `TestCacheCancelledCallerDoesNotCancelTheSharedLoad`, `TestCachedOverviewAgesWhatItServes`, `TestCachedQueueAndStorageAgeIndependentlyAndBlankWhenExpired`, `TestServiceOverviewServesAnAgedCopyAfterAFailedRefresh` (RED: "ingest up, age 5s" three minutes later), `TestCrawlersPageShowsWhenItWasReadAndWarnsWhenItIsCached`, `TestCachedCrawlerPageAgesItsActivity`.

## 4. Security follow-up: pending email-verification revocation

A sub-agent implemented it in an isolated worktree on top of the baseline and its commit was cherry-picked here (`fix(web): revoke pending email verification links on every password write`); the design and the tests below are its report, whose commands I did not re-run except as part of the full suites of section 7.

**Finding (Medium, accepted by the owner).** A password change, reset, setup completion or administrator `set-password` revoked sessions and tokens but left the account's outstanding `email_verify` links valid (up to 24 hours). A link mailed before the change (for instance requested by someone with a briefly hijacked session, to a mailbox they control) could still confirm or replace the account's email address after the credentials were rotated; a request authorised with the old password could also create a new pending link after the change had committed. **Impact:** the address that serves as the password-recovery channel could be taken over after the owner believed the account was secured.

**Fix.**

- Every password write deletes **all** of the account's `email_verify` links in the same transaction as the password update, under the user-row lock (`deleteEmailVerifyLinksTx`, called from `resetRevocationsTx`, which covers password-link completion for reset and setup and the CLI `set-password`, and from `ChangePassword`). It writes nothing to `users`: a **verified address stays verified**, an unverified stored address stays stored and unverified; only the **pending link** (including a pending replacement address) is cancelled. A rollback undoes the deletion. Writers that do not qualify: the login rehash (the same password in a newer format), registration and the offline user migration (new accounts).
- *Completion race.* `CompleteEmailVerify` already locks the user row before consuming its link; its `DELETE` is re-evaluated after the lock wait (READ COMMITTED), so a completion racing a password change either runs first or finds its link deleted (`ErrLinkInvalid`).
- *Issuance race (real).* `postEmail` verified the password and then issued the link, and `postEmailResend` only had the session: a password change committing in between let an old-credential request recreate a link. `Store.IssueEmailVerifyLinkForSession` now locks the user row and requires that exact session to still exist and be unexpired (the same test as `ChangePassword`); every password write deletes the account's sessions under the same lock, so either the change committed first (the session is gone, nothing is written, the handler redirects to `/login`) or the issuer locked first (the change then deletes its link). Rejected alternatives: a password-hash comparison (it would fail spuriously on a concurrent login rehash, and `resend` has no verified hash) and a credential-version column (unnecessary).
- Session, API-token and RSS-token revocation policies are unchanged; no API contract changed (no OpenAPI change); no new database privilege.
- Updated: `docs/specs/web-v1.md` (§4.7, §4.9.5, §4.9.6, new §4.9.11, §4.10, §5, new §14.11, revision 10), `docs/web-deployment.md`, `UPGRADE.md`, `docs/migration_0.8.0.md`, the account page hint and post-change notice, the `password-set` login notice, the reset/setup page and email, the verification email and the CLI output. The wording distinguishes preserving an already verified address from the invalidation of outstanding links.

**Regression tests** (RED first at store level: `revocations.EmailLinks = 0` in all 12 path × address-state combinations, issuance authorised before the change succeeded, completion racing the change succeeded; the handler tests were mutation-checked by disabling the deletion and the session check): `internal/web/accounts` — `TestPasswordSettingInvalidatesPendingEmailLinks` (every password-setting path against no address, an unverified and a verified address), `TestPasswordSettingWithoutPendingLinkReportsNone`, `TestPasswordSettingRollbackKeepsPendingEmailLinks`, `TestFailedPasswordChangeKeepsPendingEmailLink`, `TestPasswordSettingLeavesOtherAccountsEmailLinks`, `TestRaceSessionBoundIssuanceVersusPasswordChange`, `TestRaceEmailCompletionVersusPasswordChange` (both orders), `TestIssueEmailVerifyLinkForSession`, `TestFreshIssuanceWithRotatedSessionAfterPasswordChange` (a fresh link is issued and completed after the change); `internal/web/account` — `TestPasswordChangeAndResetCancelPendingEmailLinkButKeepVerifiedAddress` (including password recovery), `TestPasswordChangeKeepsUnverifiedAddressAndResendWorks`, `TestEmailRequestAuthorizedBeforeAPasswordChangeCreatesNoLink`; `internal/web/admincli` — `TestSetPasswordCancelsPendingEmailLinkButKeepsTheAddress`. The existing recovery and email-replacement flows keep their tests (the old test that pinned "the link survives a password operation" was updated to the new contract).

**Residual limitations.** A pending replacement address is lost on a password change and must be requested again (the page and the documentation say so); a confirmation email already delivered shows the generic "link cannot be used" page; the session re-check covers session-authorised issuance (the only way the account page issues links), while `IssueEmailVerifyLink` without a session is for registration and tests and carries no credential check; a request authorised by a session that a password change deleted is redirected to `/login` instead of getting an error page; a completed replacement still notifies the old address as before.

## 6. Deferred 07J tests (issues #52 and #53)

**#52 `TestVerifyDecodeFinalizedRunNotInterruptedByCancel` — a product defect, fixed.** *Question of the issue:* does the race affect production, or only the harness? *Answer:* production. When the cancellation (Ctrl-C, SIGTERM) lands after the server committed the verification verdict but before the client received the commit acknowledgement, `FinishVerification` returns an error although the verdict is durable; the pass then took the cancellation branch, tried to mark the already finished run interrupted and reported `ErrInterrupted` with "marking the pass interrupted also failed: migration run state is corrupt or inconsistent" — a wrong exit status and a misleading message for a completed run. The shared finish path (`verify-decode` and `verify-content`) now reconciles an ambiguous finish against the stored row on a detached context and reports the stored verdict. *Deterministic reproduction:* `TestVerifyDecodeVerdictCommittedBeforeTheAcknowledgementIsNotAnInterruption` runs a TCP fixture that forwards the finishing `COMMIT` and holds its acknowledgement while the test cancels the pass — RED with the exact message of the issue, GREEN with the fix; the poller-based test passes under every ordering (36 runs in 6 parallel processes).

**#53 `TestNearExhaustedDeadlineAfterGateWaitStartsNoStatement` — a harness assumption, made deterministic.** The test freed the gate with a real timer and asserted that the gate was drained right after `Search` returned; a late timer lets `Search` time out while still queued, before the slot is released. Not reproduced in 1,800 stress runs, so the explanation rests on the code. The test now queues the request, sets the deadline it needs and releases the slot explicitly (a context whose deadline the test controls): no timer is in the outcome; 1,800 stress runs pass.

**#53 `TestConcurrentIdenticalMissesCollapse` — already deterministic.** Its earlier failures came from a wait condition that let late starters begin after the gate opened (fixed in Task 05: `2*(n-1)` joined hashes). 9,600 iterations under 8-way CPU load with `-race`: no failure. No change.

**New, found by the clean-checkout race run: `TestSenderDrainsABacklogBackToBackWithOneRequestInFlight` — harness assumption, made deterministic.** It measured "the second full batch left within 400 ms" from before 600 durable SQLite appends; under `-race` on a busy host the appends alone exceed the window (second batch after 600 ms). The queue is now filled before the sender runs and the linger is 6 s, far longer than any scheduling delay; 96 stress runs under load pass. The sender code did not change.

The `-p 3` workaround: section 7 reports the default-parallelism run.

**Reading.** At a production-like rate the criterion of the plan is met by a wide margin: with the statistics locked admission throughput is **100 % of the baseline**, **nothing is refused**, the queue never exceeds one batch (the consumer keeps up: the backlog drains in under a second after the load stops), and no warning or error line comes from anything but the statistics themselves. The cost of the sabotage is **entirely the cost of its method**: an open transaction pins the vacuum horizon of the whole database (121,218 transaction ids behind, 300 s) whatever it holds, so the hot single-row `usage` table and the queue accumulate ~60,000 dead tuples each (autovacuum runs five times and cannot remove them), and admission latency rises by about 1 ms at p50 (2.3 → 3.3 ms) and 1.7 ms at p95. The unrelated idle transaction produces **the same** numbers (3.33 / 4.32 / 4.74 ms, 59,976 / 61,142 dead tuples) as the locked statistics, which is what the Task 09 control showed at saturation: the statistics code adds nothing to it. The enabled-without-sabotage rows show the instrumentation's own cost at this rate is not measurable against the control (p95 2.55 against 2.62 ms, inside the noise).

**Statistics conservation.** After the release the persisted totals equalled what had been recorded: received 66,000 = acknowledged 66,000 + refused 0, = enqueued 66,000 + duplicates 0, for the enabled and the enabled-locked runs (the producer saw 60,000 acknowledged in the measurement window; the other 6,000 are the warm-up).

**Backlog recovery — two defects of the statistics writer found by this run and fixed.** (1) In the first run both locked rounds timed out waiting for the persisted totals to catch up for 90 s after the release (the admission figures were unaffected and were recorded; first-run log in `raw/sabotage-rate.first-run.log`). The retry pause after a failed attempt was up to a minute counted from the *end* of the attempt, so the next 60 s tick still fell inside it and was skipped: under a sustained failure the statistics retried every 120 s (`TestRetryDelayNeverSkipsTheNextTick`; the pause is now at most a quarter of the interval). (2) With that fixed the catch-up took **89 s** in both rounds (`raw/sabotage_rate.locked-before-recovery-fix.jsonl`): the recovery tick applied the sealed batch only and what had piled up behind it waited for the next tick. A flush now applies the sealed batch and then what waits (`TestRecoveryAppliesTheSealedBatchAndTheCarryInOneFlush`, RED with 6 of 24 persisted): the catch-up is now **29 s** (`raw/sabotage-rate.locked-after-recovery-fix.log`). Neither defect touched admission, authentication or conservation.

**Not claimed.** A saturating load with the statistics locked still shows the Task 09 ratio (it measures the vacuum-horizon cost of an open transaction under 90,000 records/s). Vacuum behaviour under a *real* long transaction in production (a forgotten `psql` session) is the same effect: an operator-facing note is in `docs/operator-statistics.md`.
