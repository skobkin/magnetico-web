## S2 review corrections

1. **PHC length bound.** `parseArgon` rejects any string longer than `maxPHCLen = 256` before splitting or decoding (the longest valid
   form is 206 characters: 64-byte salt and key at m=65536,t=10,p=16). No parameter bound was loosened. Tests: the longest valid
   string still parses; oversized salt/key fields, a 1 MiB hash, 4 MiB of `$` and a 1 MiB bcrypt-prefixed string give
   `ClassUnsupported` / `ErrUnsupportedHash`; `AllocsPerRun` on a 4 MiB input is 0.
2. **Dummy hash.** `Service.Prepare(ctx)` computes the reference once (serialised by a cancellable one-slot gate, through the shared
   limiter; a failed or cancelled attempt leaves the service unprepared and retryable). `DummyVerify` performs exactly one
   verification and returns `ErrNotPrepared` until `Prepare` succeeded; W3 must call `Prepare` before accepting logins. Tests:
   16 concurrent `Prepare` calls observe one reference and a prepared service does not re-enter the limiter; `ErrBusy` and
   cancellation leave it retryable; waiting for the gate honours the context.
3. **Cancellation.** `Limiter.Do` checks `ctx` before admission and again after obtaining a slot, so `fn` never starts under a cancelled
   context; documented that a running Argon2/bcrypt computation cannot be interrupted and that no goroutine simulates cancellation.
   Tests: pre-cancelled `Do`, `Hash` and `Verify`; cancellation while waiting, then the slot frees.
4. **Memory test.** Only the heap growth (128 MiB observed against a 256 MiB budget) is asserted; RSS is logged as diagnostic.
5. **Run:** `go build ./...`, `go vet ./...`, `go test -race -short ./internal/web/password` and `go test ./internal/web/password`
   (34 PHP vectors, memory test): all passed.

## Steps 7–8: account stores and operator CLI

**Account store** (`internal/web/accounts`, SQL only; inside `./internal/web/...` so the W1 import-boundary test covers it — a small
deviation from 07A §4.1's `internal/users`). Users, one-time password links, invitations, API tokens, RSS tokens; lock order invite
row → user row → dependent rows; every one-time-token write under the user row `FOR UPDATE`; `active` read inside the locking
statement; expiry always by the database clock; revocation only ever `NULL → now()`; secrets stored as SHA-256 only; each token type
has its own table and its own `Authenticate*` function (no routing on prefixes).

**Operator CLI** (`internal/web/admincli`, `opflags/web_admin.go`, `main_webadmin.go`): `web user add|list|set-role|disable|enable|
reset-password|set-password|revoke-tokens|invite add|list|revoke` and `web tracker list|add|remove|move`. `web` is now
`subcommands-optional`; bare `web` is unchanged. Each command validates only what it uses (database always; public URL only where links
are printed; `invite-quota` only for `user add`). A stray positional argument is a usage error that does not echo it.
`set-password` reads a no-echo TTY prompt twice through `golang.org/x/term` v0.48.0 (added at this first use) or one piped line; never
argv. Tracker writes run under the same advisory key as the seed and renumber densely. `webdb.OpenOperator` opens two connections and
verifies structure and the operator privileges.

**Deviations / notes.** (1) A hash given to the store must classify as supported (current or legacy); the store does not hash.
(2) `ListUsers` carries the stored hash inside the process only so the CLI can classify it; it is never printed. (3) The invite status
`suspended (owner disabled)` shows no link. (4) Tracker URL validation lives in `accounts` (`ValidateTrackerURL`) and is reused by the CLI.

## S3 review corrections

1. **Expiry after lock waits.** PostgreSQL `now()` is fixed at transaction start, so a transaction that waited for the user row lock could
   accept a credential that expired meanwhile. Fixed without changing lock order or atomicity:
   - `CompletePasswordLink`: the consuming `DELETE` compares `expires_at > statement_timestamp()`; that statement runs after the user
     row lock is held.
   - `RegisterWithInvite`: after the owner's `FOR SHARE` lock, a new statement re-checks the invitation's expiry against
     `statement_timestamp()` before the user is created; the consuming `UPDATE` repeats the guard. A refusal rolls back, so the
     invitation stays unconsumed and no user or quota invitations remain.
   - Related paths: lifetimes of newly issued links and invitations are now computed from `statement_timestamp()` too (they are written
     after a possible lock wait). Authentication and invitation listing are single statements without lock waits, so `now()` is correct
     there; recorded timestamps (`revoked_at`, `used_at`, `password_changed_at`) intentionally stay transaction time.
   - Tests (`expiry_test.go`, deterministic): a separate transaction holds the user row lock, the operation starts while its link or
     invitation is still valid and is observed blocked in `pg_stat_activity`, the test waits on the database clock until expiry, releases
     the lock, and asserts `ErrLinkInvalid` / `ErrInvitationUnavailable` with the link or invitation unconsumed and no other state
     changed (credential rows byte-identical, tokens not revoked, no user created). Both tests failed on the previous code and pass now.
2. **Withdrawn by the reviewer:** the proposed credential-revocation warning for setup links. The CLI keeps the warning for reset links
   only; passwordless accounts normally have no issued credentials (the store technically permits tokens for them, an accepted edge case).
