# Magnetico 0.8.0 — PostgreSQL Persistence Contract (revised draft v2)

**Status:** Revised implementation draft incorporating October 2026 decisions. Builds upon `magnetico_wire_format_v1_spec.md`. This document does **not** implement a database migration or the future Go web UI.

## 1. Baseline → proposed model

Both `boramalper/magnetico` and `tgragnato/magnetico` currently have `torrents(id INTEGER, info_hash BYTEA UNIQUE, name TEXT, total_size BIGINT, discovered_on INTEGER)` and a `files(id INTEGER, torrent_id INTEGER, size BIGINT, path TEXT)` table. The `tgragnato` fork additionally migrates `files` to **100 HASH(id) partitions**, indexing `torrent_id` and `path` with B-tree and GIN trigram respectively.

| Change | Original `boramalper` | Fork `tgragnato` | New 0.8.0 |
|---|---|---|---|
| `torrents` | Existing | Existing | Kept, plus `file_count` and `discovered_on BIGINT` |
| `files` | Unpartitioned rows | Partitioned rows + path GIN | Removed |
| File content | One row/file | One row/file | At most one blob/torrent |
| File lookup | JOIN all file rows | JOIN partitioned file rows | PK lookup + codec decode |
| Name search | `pg_trgm` | `pg_trgm` | Kept on `torrents.name` |
| Search by file path | None in original version | Included in fork | Deliberately removed for 0.8.0 |
| Automatic `files` v0→v1 migration | No | Yes | Entirely removed; dedicated offline migrator |

**Conceptual diff (both upstreams → new schema):**

## 2. Proposed DDL (new database, not ALTER statements)

```sql
-- Must already be installed by the database owner/admin:
-- CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE SCHEMA IF NOT EXISTS magneticod;

CREATE TABLE magneticod.torrents (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    info_hash BYTEA NOT NULL UNIQUE,
    name TEXT NOT NULL,
    total_size BIGINT NOT NULL CHECK (total_size > 0),
    discovered_on BIGINT NOT NULL CHECK (discovered_on > 0),
    file_count INTEGER NOT NULL CHECK (file_count > 0)
);

CREATE INDEX idx_torrents_total_size
    ON magneticod.torrents (total_size);
CREATE INDEX idx_torrents_discovered_on
    ON magneticod.torrents (discovered_on);
CREATE INDEX idx_torrents_name_gin_trgm
    ON magneticod.torrents USING GIN (name gin_trgm_ops);

CREATE TABLE magneticod.torrent_file_blobs (
    torrent_id INTEGER PRIMARY KEY
        REFERENCES magneticod.torrents(id) ON DELETE CASCADE,
    data BYTEA NOT NULL CHECK (octet_length(data) >= 2)
);
```

`info_hash` length check is intentionally unresolved until the audit of v1, v2-only and hybrid metadata: do not assume a 20-byte hash for every future supported torrent. Continue using `INTEGER` IDs as agreed; the migration must check that the existing ID range and expected growth fit a signed 32-bit integer. Failure is a **blocking** issue to resolve before schema freeze; silently renumbering IDs is not allowed. Following offline import with explicit IDs, reset the identity sequence to a value above the imported maximum.

No user-account tables appear here; migration from Symfony is a **separate command/phase** and its failure cannot invalidate torrent migration progress. A future `users` schema can coexist in the same PostgreSQL database.

At startup both crawler and web must test availability of `pg_trgm` and expected schema version, fail fast with actionable instructions if absent/incompatible, and **must not silently attempt the fork's old automatic migration**. No requirement for the application database role to create privileged extensions.

## 3. Persistence API (illustrative, not binding Go signatures)

```go
type Torrent struct {
    ID           int32
    InfoHash     []byte
    Name         string
    TotalSize    int64
    DiscoveredOn int64
    FileCount    int32
}

type File struct {
    Path string
    Size int64
}

// Existing semantics should be preserved, but adapt method names and context
// consistently when implementing the repo's storage interface.
type Store interface {
    AddTorrent(ctx context.Context, meta Torrent, files []File) (created bool, id int32, err error)
    GetTorrent(ctx context.Context, infoHash []byte) (Torrent, error)
    GetFiles(ctx context.Context, infoHash []byte) ([]File, error)
    QueryTorrents(ctx context.Context, query TorrentQuery) ([]Torrent, error)
    GetStatistics(ctx context.Context, query StatisticsQuery) (Statistics, error)
}
```

The interface is deliberately small and PostgreSQL-first. Other database implementations, e.g. SQLite, are **not** 0.8.0 requirements. API results and name/RSS search must **not** need to decode blobs; `file_count` and `total_size` come from `torrents`.

## 4. `AddTorrent`: encode outside transaction, insert atomically

1. Validate `info_hash`, torrent metadata, `len(files)`, nonnegative sizes, path constraints and checked sum equal to `total_size`. Preserve exact path bytes after ingestion's accepted validation. No silent repair of invalid metadata.
2. Detect no-blob eligibility **only if** `len(files)==1 && files[0].Path==meta.Name && files[0].Size==meta.TotalSize`. This holds for typical v1 single-file data but is not automatically true for all v2 or legacy records. If the optimization causes a verified integration conflict, implementation may disable it while preserving the decoder's handling of blobs.
3. If blob needed, canonicalize a copy, encode using configured profile, and enforce all limits **before opening** a database transaction. Compression is CPU work; it should not unnecessarily hold locks.
4. Begin transaction, execute `INSERT INTO torrents ... ON CONFLICT (info_hash) DO NOTHING RETURNING id`. For a newly inserted row, insert matching `torrent_file_blobs` row if needed; commit both changes together. On any failure, roll back everything.
5. If the infohash was already present, return a typed `AlreadyExists` outcome instead of changing metadata or overwriting its blob. Log meaningful conflicts if the same hash has inconsistent metadata. Do not perform `DoesTorrentExist` followed by an unprotected insert as the concurrency-control mechanism.
6. Use a bounded worker pool for encoder ownership and reuse (`Reset` when supported); constrain memory and number of active DB operations separately. Do not share mutable compression state across goroutines without synchronization.

Encoding may be expensive; checking hash existence before encoding as a **performance hint** is allowed, but uniqueness/transaction handling remains the authority. Avoid encoding the file list of already-known torrents where possible.

## 5. `GetTorrent` / `GetFiles`

`GetTorrent` fetches only `magneticod.torrents`: it must not join/scan/decompress blobs. `QueryTorrents`, RSS, sorting and statistics likewise operate on metadata (`file_count`, `total_size`). The `tgragnato` filename `ILIKE` predicate and statistics `JOIN files` must be removed/refactored.

`GetFiles(infoHash)`:

1. Read `torrents` row by `info_hash` and optional blob by `torrent_id`; do **not** interpret an absent torrent as an empty file list.
2. If `file_count==1` and blob is absent, return a single file `(name, total_size)` (the intentional no-blob representation).
3. If `file_count>1` and blob is absent, return typed `ErrIntegrityMissingBlob`, log `torrent_id`/infohash and emit a bounded alert signal. Never return an empty file list as success.
4. If blob exists, decode boundedly, verify the internal count, canonical ordering rules, total decoded size (checked against overflow) and no trailing data; return the whole list or `ErrCorruptBlob`, **never a partial list**.
5. A single-file blob is valid and may carry a name different from `torrents.name`; never assume `file_count==1` means blob is forbidden.

**Known integrity limitation:** loss of an atypical `file_count==1` blob is undetectable from the new schema alone. Cross-check the original file list during migration verification while the source DB still exists. Do not add a dedicated blob-existence flag (agreed storage optimization trade-off).

Use typed error categories, e.g. not found, unsupported codec/version, corrupt payload, invariant mismatch, storage I/O failure. Distinguish HTTP 404 (unknown torrent) from HTTP 500 (database corruption) when web integration is implemented.

## 6. Startup checks and ongoing integrity

- `pg_trgm` installed; expected tables/indexes and schema version present; supported migration state; PostgreSQL privileges/connectivity checked with useful errors.
- No implicit legacy migrations or production-altering data conversion on startup.
- `magnetico migrate verify-decode --workers N`: after offline conversion, scan **all torrents** in bounded ID ranges, read and decode every existing blob, validate counts, sizes, canonical records, overflow and truncation; explicitly flag every `file_count>1` row missing a blob. Handle the no-blob single-file exception. This check only needs the **target** database.
- Record failures with `torrent_id`, infohash, category, expected/actual fields and bounded diagnostic context; export as machine-readable JSONL. No full paths in routine logs.
- `magnetico migrate verify-content --workers N`: **preferred final cutover gate**. In addition to target decoding checks, compare all original and migrated torrents, including exact `(Path,Size)` multisets in canonical order, file count, metadata and historical IDs, reading from the read-only original DB. This detects a lost atypical single-file blob that verify-decode alone cannot detect. Use bounded streaming/batches; measure and expose throughput and ETA so an operator can make an informed decision about a slower full-content pass. A successful decode alone does not prove all original records were migrated correctly.
- Idempotent, bounded, parallel workers are acceptable, but verification must not overwhelm a remote or production PostgreSQL instance. Test with realistic pool limits.

If `file_count>1` is missing its blob: while original DB still exists, re-read source and re-encode only that ID using migrator retry-errors; after cutover, restore from backup or attempt DHT re-fetch with explicit errors. Do not invent an empty list or silently delete the torrent.

## 7. Migration operational interface (separate workstream)

The migration schema is separate: `magnetico_migration.progress` and `magnetico_migration.errors` are **temporary operational tables**; the permanent application's schema-version tracking remains even after cleanup.

```text
magnetico migrate torrents
magnetico migrate torrents retry-errors
magnetico migrate users                  # separate source DB and checkpoint
magnetico migrate users retry-errors
magnetico migrate errors export --format jsonl
magnetico migrate errors export --format jsonl --include-records --source-db-env MAGNETICO_MIGRATION_SOURCE_DSN
magnetico migrate errors export --format jsonl --include-records --include-blobs --source-db-env MAGNETICO_MIGRATION_SOURCE_DSN
magnetico migrate verify-decode --workers 8
magnetico migrate verify-content --workers 8
magnetico migrate cleanup
```

The first migration is offline: old indexer and PHP UI stopped, old data read-only, destination newly initialized. Display an interactive progress bar with absolute processed/total, migrated/skipped/failed counters, throughput, elapsed and smoothed ETA; non-TTY output must use periodic structured log records. Accurate resume must retain a consistent overall progress value. Process in batches; commit the data, error registry and batch checkpoint transactionally. With parallel encoding, **advance the checkpoint only over a contiguous set of committed source IDs** (or use explicit completed-batch states), never to the maximum finished worker ID if earlier work is unfinished. Retry-errors must read IDs from `magnetico_migration.errors`, not rescan every old file. Every operation must be idempotent.

`cleanup` removes **only** migration bookkeeping, must require explicit user intent and successful verification, and cannot erase the permanent schema version table. Production cutover is one coordinated event after separate migration of torrents and users, their validations, and backup confirmation.


### 7.1 Forensic export of failed records (migration phase, required)

`migrate errors export` must support an **optional** `--include-records` mode in addition to standard error-only JSONL. The augmented output must be useful for agent-assisted analysis of each failed torrent **without direct access to the original databases**: failure stage/type/message, `torrent_id`, `info_hash`, source torrent fields, original per-file `path` and `size` entries (preserve duplicates), and the corresponding target record and metadata when present. Do not silently rewrite invalid records or normalize paths. If byte-exact representation is required for unusual source values, use reversible encoding (e.g., Base64), not lossy string replacement.

Optionally include exact new `torrent_file_blobs.data` bytes via a distinct **explicit** `--include-blobs` flag (Base64). The ordinary JSONL export must not require either database's full data beyond the error registry; `--include-records` requires read-only access to the original source DB configured through a secret-safe environment variable or protected config (not via a password-bearing CLI flag) and must fail clearly if that source is unavailable. Output is streaming/bounded, with explicit per-record and total limits, no silent truncation, deterministic field schema, and an optional manifest/version/checksum. The export operation is read-only; never include DB passwords, application auth tokens, or unrelated user data. Output may contain private torrent names and paths: mark it sensitive and use restrictive file permissions.

`migrate ... retry-errors` revisits only IDs stored in the error registry. `migrate cleanup` explicitly removes temporary bookkeeping only after successful verification/operator approval; a permanent schema-version record remains.

## 8. Structured events and optional notifications

Log `torrent_id` whenever known, plus `info_hash`, `operation`, `error_category`, `limit_name`, `expected`, `actual` and failure cause as applicable. For rejected incoming DHT metadata before DB insertion, infohash is the primary identity. Do not emit arbitrary filenames or sensitive details by default.

- Harmless structural fallback to flat/prefix: debug/aggregated counter, not one warning per torrent.
- Incoming metadata exceeding configured limits: `WARN`, fail that entry safely, aggregate to avoid notification floods.
- Corrupt/missing stored blob or broken referential invariant: `ERROR`, no silent recovery; eligible for optional exception sink.
- Migration failure: recorded in error table, surfaced in summary and JSONL export. Cutover blocked until resolution or separately documented explicit operator decision.
- Notification integration via a small optional interface (future Sentry, Shoutrrr/ntfy). Neither Prometheus nor Sentry is a prerequisite for 0.8.0.

## 9. Tests and acceptance gates

- Empty, single-file no-blob, atypical single-file with blob, ordinary multi-file, duplicates and zero-size member files (while torrent total >0), unusual paths, UTF-8 and invalid metadata.
- Transactional rollback when blob insert fails, no orphan blobs on deletion, concurrent infohash insertion race and idempotent duplicate handling.
- End-to-end metadata-only search/RSS/statistics without blob decompression; file page loads exactly one blob and reconstructs full sorted list.
- Fail fast for missing `pg_trgm`, unsupported schema version and no permission to read/write.
- Inject corrupted blob, unsupported version and mismatched file counts/sizes. Verify typed failures; never report success or silently repair.
- PostgreSQL fixture-based CI (ephemeral Woodpecker PostgreSQL) and separate old-schema migration fixtures. Distinguish `boramalper` original and `tgragnato` partitioned layout when testing legacy imports.
- Audit BitTorrent v2/hybrid metadata extraction before deciding whether support belongs in 0.8.0. Preserve original paths accurately; no `.torrent` reconstruction requirement.

## 10. Pending design choices for review

1. **Agreed:** preserve existing torrent IDs during migration. Check signed `INTEGER` capacity and source sequence state **before implementation**; stop and revisit type before migration on overflow risk.
2. **Agreed:** implement both full `verify-content` (preferred cutover gate) and target-only `verify-decode` (operator fallback when a full source read is too slow). Show elapsed/ETA and truthfully mark what was not checked.
3. Precise error enum/API names and retry behavior, to be set after looking at the fork's existing interfaces.
4. Codec-level UTF-8 policy vs. ingestion-level validation for anomalous peer metadata: preserve accepted historical path bytes and reject new records according to explicit policy, not ad-hoc normalization.
