# Magnetico 0.8.0 — Forensic Export & Operational Cleanup Contract (Task 04C)

**Status:** Proposed normative supplement for owner review, not implementation authorization.  
**Baseline:** `skobkin/magnetico-web`, `refactor/0.8.0-unify-and-new-storage`, accepted Task 04B at `cd5d0c5b`.  
**Parents:** `docs/specs/legacy-torrent-migration-v1.md` §8 and §10; `docs/specs/legacy-torrent-verification-recovery-v1.md` §§2, 5–7; `docs/specs/postgresql-persistence-v2.md`; `docs/specs/wire-format-v1.md`; `docs/engineering-standards.md`.

This supplement defines the **04C** scope only: `migrate errors export` and `migrate cleanup`. It does **not** authorize production cutover, 04D testing, schema/wire changes, source writes, user migration, crawler/web work, or general repair of corrupted target rows. The original source is boramalper/magnetico v0.12.0 (unpartitioned `magneticod.files`).

## 1. Commands and safety model

```text
magnetico migrate errors export --output migration-audit.jsonl --manifest
magnetico migrate errors export --output forensic.jsonl --include-records --manifest
magnetico migrate errors export --output forensic-with-blobs.jsonl --include-records --include-blobs --manifest

magnetico migrate cleanup                     # dry-run / preflight only (default)
magnetico migrate cleanup --execute --confirm-backup --confirm-export --evidence-manifest migration-audit.jsonl.manifest.json
magnetico migrate cleanup --execute --force-unverified --reason '...operator reason...' --confirm-backup --confirm-export
```

Names are proposed CLI spellings; maintain current `migrate` parser/config precedence. The target DSN uses the existing `--database` / `MAGNETICO_MIGRATE_DATABASE` / `migrateDatabaseURL` path. Source access, **only** for `--include-records`, uses `MAGNETICO_MIGRATION_SOURCE_DSN` or `migrateSourceDatabaseURL`; no source DSN flag or fallback to target. `--include-blobs` requires `--include-records`. Never expose passwords in process arguments or logs. `--output -` (stdout) is permitted for **metadata-only** export, never for record/blob export. Progress and warnings go to stderr; stdout must remain valid JSONL.

Two deliberately different preflights:

- **Export is diagnostic, fail-open with respect to import completeness/data consistency, fail-closed on unsafe structure or connections.** It must work on an interrupted/failed import, `import_complete_with_errors`, and a target with data/count mismatches. Do not call `target.CompletedRunPreflight` or require `state.Reconcile` for exporting. Do not mutate, initialize, or automatically upgrade an operational schema. Purely inspect v1/v2 operational relation **definitions** and the recorded run. Prefer exporting even when the permanent target schema is damaged, if operational history is structurally readable. A malformed or ambiguous operational schema is an explicit error, not a guessed export. Metadata-only export must not require or contact the source.
- **Cleanup is destructive and fail-closed.** Require a completed, consistent import; strict permanent schema; authoritative successful, current verification gates; operator-confirmed backups; an independently durable forensic/audit export; explicit execution flags; and the existing exclusive migration advisory lock. A narrowly documented `--force-unverified` override can waive *verification findings* only, not schema ownership/inventory, consistency, a completed import, concurrency, backup confirmation, or explicit execution. See §6.

Both acquire the same migration advisory lock used by 04A/04B, and monitor lock liveness. The lock only excludes migration commands, **not arbitrary application/DB writers**; operator-enforced offline state remains required. Only PostgreSQL test databases are allowed during implementation; no production contact or restored 10% dataset.

## 2. Export scope, history and stable JSONL contract

Default export is **source-independent, metadata-only**, complete for the selected migration run. It must include **both resolved and unresolved** import errors; all run-scope incidents; every 04B retry attempt (including unsuccessful/missing-source); and all verification issues (including older runs and informational provenance). Preserve the original error row, `attempts`, `resolved`, `resolved_at`, its stable stage/category/code and safe details. Include bounded, sanitized summaries of import progress, verification runs and retry runs, so a clean migration still has an audit artifact with revision and verdict provenance.

Use a versioned JSONL envelope, for example:

```json
{"format":"magnetico-migration-forensics","format_version":1,"type":"import_error","run_id":"...","error_id":3,"scope":"record","source_id":42,"stage":"validate","code":"invalid_metadata","resolved":true,"attempts":2,"details":{}}
```

The example is a shape, not a command to hardcode error codes. Each line is **one valid JSON object**, with deterministic field names and ordering of events. Types should include `export_header`, `import_run`, `import_error`, `verification_run`, `verification_issue`, `retry_run`, `retry_attempt`, and `export_footer`. Exact source identifiers use original numeric IDs; infohash, when included, is explicitly represented (hex or Base64, documented). Include the schema/format version, run UUID, source table ID, verification/retry UUID, and issue/attempt identity wherever relevant. Do not assume arbitrary stored JSONB diagnostic strings are harmless: whitelist known safe fields or conservatively redact unknown/free-text fields in the metadata-only mode; keep original raw records behind the explicit sensitive-export option. Do not accidentally report a historic pass as a *current* pass: compute latest authoritative verification per **kind** by 04B's highest `verification_runs.seq`, and require `state='completed_pass' AND start_data_revision=progress.data_revision` for a current pass. Older successful results remain visible as historical, possibly stale evidence. For v1 operational state, emit v1 import/error events and mark the 04B-only collections unavailable, not silently empty.

Export **all rows** by default. Do not silently truncate. Support explicit selection filters (at least `--only-unresolved` and `--verification-id` if manageable) without making them the default and record filters in the header/manifest. Support bounded keyset pages over every table (`errors.id`, `verification_runs.seq`, `verification_issues.id`, `retry_attempts.id`, etc.), stable order, and no full-result in-memory maps. A bounded page should be enough to resume an internal read, but 04C need not persist an export checkpoint: partial files are not final artifacts and an interrupted export is restarted. Do not invent external incidents absent from the DB: an incident that could not be persisted during an outage is unavailable to DB-only export.

**Data model note:** 04B report's “history is immutable” means normal migration/verification/retry operations may not rewrite history; a separately confirmed, terminal cleanup deliberately removes the **whole** temporary operational schema, including history. Never silently delete individual history rows while leaving the schema otherwise active.

## 3. Explicit full-record forensics

`--include-records` is an **opt-in sensitive export**. For each distinct selected source ID mentioned by an import error, retry attempt or verification issue, export a reversible, exact source/target snapshot (or explicit absence). Use a deterministic reference key so multiple findings referencing one source ID can link to one record snapshot; do not require an unbounded global deduplication map. A bounded merge of ID-sorted cursors or equivalent set-oriented keyset queries is preferred. Avoid a source-file query per source row when batching is feasible.

Source snapshot must include all original torrent fields (`id`, exact 20-byte `info_hash`, `name`, `total_size`, `discovered_on`) and **every** matching source file row (`files.id`, nullable owner where relevant, exact `path`, `size`), preserving duplicate `(path,size)` entries and **source file IDs**. Do not enforce the production codec's 50,000-file limit as a forensic truncation: a malformed oversized source record needs its complete files too. Stream arbitrarily large file lists in bounded pages, preferably as typed JSONL `source_record`/`source_file` events keyed to the same record reference, rather than collecting a single gigantic array. File-row order is not a target identity, but export it deterministically (`files.id`). Do not normalize paths/names.

Target snapshot includes whatever exists: original target `id`, infohash, name, total_size, timestamp, file_count, blob presence and stored blob length, plus **the decoded file list when decoding succeeds**. For intentional no-blob `file_count=1`, identify the reconstructed `(name,total_size)` entry as an **assumption**, not proof of original source content. For missing/unreadable blob, include a typed decode/structural error and preserve all other available metadata; do not make decoding success a precondition for producing an export. Do not mutate source or target, do not re-encode the blob, and do not assume its bytes match a fresh encoding. Run-scope entries and issues without an ID retain metadata and a clear `record_unavailable_reason`; they must not accidentally trigger a full-table data dump. Explicitly document that NULL-owner/orphan source file rows without a corresponding selected source ID are **not included** by `--include-records` unless a separately designed opt-in orphan export is implemented. Do not pretend otherwise.

`--include-blobs` adds the **exact stored BYTEA** as reversible Base64 even when `codec.Decode` fails. Binary output may use typed, ordered chunk events with a documented lossless decode-and-concatenate rule, or one field, but must be exact and checkable. Probe `octet_length(data)` before materializing: corrupted blobs can be much larger than codec limits. Enforce configurable per-blob and output byte caps; if a blob exceeds the configured cap, **fail the whole export explicitly** rather than skip, truncate or silently omit it. A higher explicit cap can be used by the operator if resources permit. Blob absence is distinct from a NULL-valued blob row.

Open the source with the existing read-only v0 adapter, enforce source ≠ target with the existing fail-closed identity logic, and use bounded read-only transactions. If source access, exact source schema, a required record, or full file retrieval fails, produce a hard export error (records can be explicitly marked missing only when the source query succeeded and proved absence). Data from two databases cannot be captured in one atomic snapshot; require quiescence and report the limitation. Do not contact source for the default metadata-only export.

## 4. Limits, output safety and reproducibility

The exporter must stream without scaling application memory with total error/issue count. Expose configurable **maximum exported events/records, total output bytes, and blob bytes**; use conservative defaults (agent proposes exact values during planning), integer-overflow-safe accounting and a bounded buffer. A limit breach is a **hard error**, never a successful partial export. Explicit filtering (`--limit`, if added) is distinct from a safety cap and must be visibly recorded as **partial coverage**, never a complete export or cleanup evidence. A default complete export may be rejected for exceeding its configured cap with a clear safe remediation.

For filesystem output, use an output file created exclusively (`O_EXCL`; reject preexisting paths and symlinks), mode `0600` regardless of umask, a same-directory temporary file, stream/flush/check the final bytes and publish atomically **without clobbering an existing destination even in a concurrent-creation race** (e.g. an OS-supported no-replace rename or an equivalent safe link-based publish). A pre-rename existence check alone is not sufficient. On failure or cancellation, remove the incomplete temporary output and return nonzero, leaving no file that looks completed. Where feasible `fsync` file and parent directory. On disk-full, writer, JSON encoding or context errors, do not claim success. Metadata-only stdout is allowed with an explicit warning that redirection permissions are the operator's responsibility; record/blob export requires a safe path. Do not print raw filenames, paths, blob content, DSNs or source credentials in routine progress/logs.

`--manifest` writes a separate `0600` JSON manifest **only after** output finalization, with SHA-256 of the **exact JSONL bytes**, export format, run ID, target revision, source/target identity observations (sanitized, not DSNs), selection/coverage filters, per-event counts, byte count, generation time, and whether sensitive records or blobs are included. If manifest creation fails, report the output as incomplete evidence; never quietly claim a complete audit bundle. Treat the manifest as a checksum/consistency aid, **not a cryptographic signature** or independently trusted backup. Validate a manifest at cleanup against the actual file SHA-256; do not trust manifest claims alone.

If export writes an `export_footer`, it must describe the actual emission count and status while staying part of the checksum. Avoid writing a success footer on incomplete output. CLI output needs a clear final summary and exit codes: `0` complete, `2` interrupted, `1` any failure (including output limits or source loss). No “success with truncated records”.

## 5. Forensic preflight and schema compatibility

Introduce a **read-only** operational-schema inspection seam. Reuse the strict catalog-definition maps and inventory validator in `internal/migration/state/schema_v2.go`, supporting exact **v1** (04A: progress/errors) and **v2** (04B: seven tables), with no `EnsureOperationalSchema` call because that performs DDL. Do not accept a marker value without validating objects. Refuse missing/foreign/partial operational structures; clearly differentiate “there is no migration history” from “history exists but is inconsistent”.

Default metadata export needs the target migration-state tables only; it **does not** require an import-complete phase, a valid `magneticod` production schema, or progress/target counts reconciled. This is essential when investigating precisely those failures. It does require a uniquely identifiable run and structurally readable migration-owned registry. Permit incomplete progress counters to appear as recorded (mark `not_reconciled` rather than inventing consistency). With `--include-records`, check availability of source and target tables before attempting to fetch them; if source schema is unrecognized, fail explicitly. Target row corruption should not prevent an otherwise readable forensic snapshot — emit the available fields and typed decode findings.

Use the existing migration advisory lock and lock-loss monitor; **do not** use `target.CompletedRunPreflight` for forensic export. No write, automatic operational upgrade, or schema repair occurs during export. A v1 export must be possible without 04B upgrade, even if that 04A run never completed.

## 6. Cleanup: gates, override, and transaction

`migrate cleanup` defaults to a **non-destructive preview** (`--dry-run` may be an alias). Show in human-readable, secret-safe form: run ID, import phase/counters/revision, number of migration-owned rows/tables, latest authoritative decode/content verification per kind (seq/state/revision), why it passes/refuses, export-evidence status, expected object drop list, and confirmation requirements. Dry-run performs **no DDL** and must never silently upgrade v1 state.

Normal `--execute` requires ALL of:

1. Exclusive migration advisory lock and live lock monitor; an intentionally **offline** target/source with external writers stopped. PostgreSQL ownership/permissions for exactly the objects being removed. A lock does not prove external writers stopped.
2. Exact recognized **v2** `magnetico_migration` schema definition and a completed 04A run at `import_complete` (not `import_complete_with_errors`); strict intact `magneticod` target schema; `state.Load`, `target.TargetFacts` and `state.Reconcile` all pass; **zero unresolved** record errors and run-scope integrity incidents.
3. For **each** of `decode` and `content`, select the verification with **highest `seq`** for that kind, not any historical pass. Require `state='completed_pass'`, `phase='complete'`, `start_data_revision == progress.data_revision`, exact expected/observed ID coverage, and zero mismatch/coverage/unverifiable issues. Any newer interrupted/aborted/failed run blocks, regardless of an older pass. Recheck all gates **under the lock immediately before DDL**, preferably inside the same target transaction that drops the objects. PostgreSQL and source equality still rely on the operator's offline guarantee; `data_revision` does not detect arbitrary writes.
4. Operator confirmation of an existing tested backup of the **target** (and preservation of the old source until cutover is approved), through explicit `--confirm-backup`; no claim the CLI independently verified the backup. Explicit `--confirm-export` and an existing metadata export + SHA-256 manifest that matches the **same run ID and current data revision**, with checksum verified against actual bytes and event counts/selection compared with the still-present registry. This export preserves diagnostic history before it is destroyed. Do not treat a filtered/limited export as adequate complete evidence. Sensitive-record export is **not** required by default.
5. `--execute` together with an explicit noninteractive confirmation (`--yes` or a single unambiguous `--execute` flag; choose and document one during planning). Never implicitly run cleanup because import or verification returned 0. No confirmation remembered in YAML/env. A dry-run may show blockers but must never remove objects.

**Override:** `--force-unverified` additionally requires `--execute`, explicit `--reason` (nonempty, bounded, recorded in output and operator-preserved audit), `--confirm-backup` and `--confirm-export`. It may waive missing/failed/stale verification results and unresolved record/integrity **findings** only; `import_complete_with_errors` counts as a **completed** import for override purposes if all recorded counters reconcile, whereas an actively importing or index-building run never qualifies; list each waived gate. It must **never** waive incomplete or inconsistent import state, wrong/foreign schema inventory, inability to take the lock, failed `Reconcile`, the permanent target schema, or uncertainty about which tables will be deleted. For incomplete/partially imported target recovery, use a separate manual DBA teardown procedure; do not silently erase the checkpoint from a partially populated target. An override without a usable full export manifest requires a separately acknowledged, documented operator exception (`--allow-missing-export-evidence` + reason); the command must warn that history will be irrecoverable. This exception is opt-in and never the default.

**Deletion:** Use one PostgreSQL transaction, SQL identifiers fixed in code (not user input), and explicit dependency-safe drops: `verification_issues` → `verification_runs` → `retry_attempts` → `retry_runs` → `errors` → `progress` → `operational_schema`, then owned identity sequences (if not auto-dropped), and finally the now-empty `magnetico_migration` schema with **RESTRICT**. `DROP SCHEMA ... CASCADE` is forbidden. `DROP TABLE ... CASCADE` is forbidden. `IF EXISTS` in the execution transaction is discouraged: a missing expected object is tampering/drift and should abort; rely on the validated inventory. Do not drop any `magneticod.*` tables, rows, indexes or `magneticod.schema_version`; preserve the PostgreSQL extension and all production data exactly. External FK/dependency or privilege failures abort and roll back the **entire** deletion; leave no half-cleaned schema. No autonomous cleanup or retry of destructive DDL after ambiguous connection failure.

On lost COMMIT acknowledgement, re-open a read-only connection and inspect authoritative catalog/protected target: complete absence of `magnetico_migration` **and unchanged production schema/data** may be consistent with success, but must be reported as an **ambiguous outcome** requiring operator confirmation unless it can be proven; never automatically repeat the destructive operation. Retain the external audit bundle across cleanup; no migration-owned tables remain to record a cleanup event.

A second cleanup invocation on an already-cleaned target is a harmless no-op **only if** the absence of `magnetico_migration` is explicit and no operation is attempted; report that past cleanup cannot be established from a missing schema alone. Do not allow `--execute` on a nonempty, unknown operational schema by treating it as already cleaned.

## 7. Required tests and acceptance

**Export fixtures (v1 and v2):** incomplete 04A run, failed/inconsistent 04A counters, `import_complete_with_errors`, 04B historical pass/fail/abort/stale runs; both resolved and unresolved record errors; run-level incidents; every retry attempt (including repeated failed passes); multiple verification runs/issues and informational drift; no errors; source unavailable (metadata export succeeds, `--include-records` fails); absent target row, NULL blob, corrupt and oversized blob; atypical one-file, duplicates and over-limit source file lists (all source `files.id` rows preserved); NULL-owner/orphan issue with no source ID (explicitly non-expandable). Validate JSONL version/shape, UTF-8 escaping, event ordering/IDs, full coverage and no accidental N+1/full-table load.

**Streaming/security:** bounded memory under large synthetic registry and file lists; disk-full/writer-error/cancel/size-limit/source-query-failure leaves **no finalized file**; permission `0600`, exclusive non-overwriting file creation, symlink refusal, manifest integrity, checksum mismatch detection, no printed paths/credentials/blobs, exact Base64 round-trip even for corrupt decoded blob; explicit hard failure for blobs beyond configured cap; source read-only; source/target distinctness. No unbounded `[]File` buildup for abnormal forensic source records.

**Cleanup:** read-only dry-run; no history/verified/no backup/no full manifest/filtered manifest/changed data revision/latest pass→fail/latest pass→interrupted or aborted/missing full coverage/integrity issue/inconsistent 04A counters/foreign schema object/partial-v2 state/dependency preventing drop; all refuse without any DDL. Confirm both verification kinds, not merely `verify-content`. Test override limitations, explicit reason and attestations, privilege errors, atomic rollback after an intentionally blocked drop, advisory-lock exclusion, SIGINT/SIGTERM, production tables and schema_version byte-for-byte unchanged, no CASCADE, already-cleaned no-op, and 04A/04B commands refusing or reporting missing state after cleanup rather than recreating it on a nonempty target.

Use only small disposable PostgreSQL 17 fixtures and a single pinned test container as needed. Do not restore the already-used 10% sample; the 04B real-data experiment is complete. Run build, vet, gofmt, lint, unit/integration tests and migration race suite. Document pass/skip counts and any infrastructure-only test retries accurately. No production connection or push without owner approval.

## 8. Deliverables and boundaries

- Implementation of `migrate errors export` and `migrate cleanup`, reusing existing migration state, source adapter, lock, source identity and codec decoder where appropriate; no broad rewrites.
- Tests and operator documentation of both command modes, sensitive-data risk, irreversible cleanup and recovery limits.
- `docs/wip/04C-forensics-cleanup-report.md` with tested invariants, negative cases, exact output schema, limitations, test census, and handoff to 04D / manual cutover.
- `docs/wip/README.md` task index update.

**No-go:** modifying `magneticod` production DDL/wire format; writing to original source; automatic schema repair/cleanup; exporting arbitrary full source database because of a run-level issue; suppressing or truncating record/blob payload without an explicit failure; letting old verification passes substitute for the latest failed run; deleting 04B history outside an explicitly approved complete cleanup; leaking credentials; or claiming backups and source/target immutability were cryptographically proven when they were merely operator attestations.
